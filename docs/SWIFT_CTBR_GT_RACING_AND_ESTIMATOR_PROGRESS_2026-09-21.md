# Swift CTBR GT Racing + Learned-Inertial Integration Progress — 2026-09-21

## 1. Executive summary

This branch has now reached a clear separation between **racing policy learning** and **autonomous state estimation**.

The main result of 2026-09-21 is:

> A strong CTBR racing policy has been trained successfully from simulator ground truth. The current bottleneck is no longer PPO/racing control; it is the high-dynamic learned-inertial / visual state-estimation stack when exposed to the trajectory distribution generated by the successful racing policy.

The current branch is:

```text
feature/swift-ctbr-rl
```

The successful GT racing policy uses:

```text
GT p, v, R
+ known-map next-gate geometry
+ previous CTBR action
        |
        v
31-D observation
        |
        v
256 x 256 x 256 ELU PPO policy
        |
        v
4-D CTBR command
[collective thrust, p_cmd, q_cmd, r_cmd]
        |
        v
body-rate PID
        |
        v
rate-priority mixer
        |
        v
motors
```

The best GT checkpoint completed up to **37 gates in 20 s** on the Easy-7 track, with **31.2 gates mean** over 20 episodes and **85% full-lap completion**.

Directly replacing GT state with the current learned-inertial estimator collapses performance. A GT-control / estimator-shadow test confirms that the estimator can diverge catastrophically during sustained racing: two 20 s episodes completed 37 truth gates while the estimator position RMSE grew to approximately **120 m** and **160 m**, with only **2 accepted visual updates out of 500 attempts** in each of those long episodes.

The next development phase should therefore focus on:

1. collecting true policy-generated high-dynamic racing trajectories;
2. evaluating the existing Body-Delta-v TCN on those trajectories offline;
3. retraining / extending the learned-motion model for racing dynamics;
4. diagnosing why direct gate-reprojection updates are almost always rejected at racing speed;
5. only after the estimator survives GT-controlled racing, reconnecting it to the PPO actor and performing residual/noise fine-tuning.

## 3. Why the old direct-motor PPO route was abandoned

The earlier learned-inertial PPO integration reused a legacy four-motor policy.

That policy had a large raw Gaussian mean and depended heavily on environment-side hard clipping. The deterministic legacy behavior was approximately bang-bang, with most sampled action dimensions already outside `[-1, 1]` before clipping.

Attempts to migrate the actor to a bounded `tanh` policy exposed the problem:

- synthetic actor-head distillation produced unacceptable behavior error;
- on-policy behavior distillation reduced the transfer error but still destroyed racing behavior;
- even scaling legacy executed actions from 1.0 to 0.99 or 0.95 materially degraded gate performance.

This established that the old PPO solution was not a good foundation for the final system.

The project therefore changed the action abstraction from:

```text
PPO -> four motor commands
```

to:

```text
PPO -> collective thrust + body rates
    -> low-level controller
    -> motors
```

This is the CTBR route used from this point forward.

## 4. Swift-style CTBR low-level controller

A dedicated CTBR action term was added:

```text
tasks/drone_racer/mdp/swift_ctbr_action.py
```

Normalized action:

```text
a[0] -> hover-centered collective acceleration
a[1] -> desired roll rate
a[2] -> desired pitch rate
a[3] -> desired yaw rate
```

Current body-rate limits:

```text
roll  : +/-10 rad/s
pitch : +/-10 rad/s
yaw   : +/-6 rad/s
```

The controller contains:

- body-rate PID;
- integrator limiting;
- throttle-cut integrator reset;
- rate-priority wrench allocation;
- motor/allocation dynamics.

## 7. Re-aligning GT training with the original Isaac Drone Racer baseline

The original `kousheekc/isaac_drone_racer` training setup was re-examined and the important large-scale PPO choices were restored while retaining the new CTBR action abstraction.

The new GT racing task is:

```text
Isaac-Drone-Racer-Swift-CTBR-GT-Racing-v0
```

### 7.1 PPO configuration

```text
parallel environments = 4096
rollout               = 24
network               = 256 x 256 x 256
activation            = ELU
learning epochs       = 5
mini-batches          = 4
learning rate         = 1e-4
gamma                 = 0.99
GAE lambda            = 0.95
PPO ratio clip        = 0.2
entropy loss scale    = 0.005
reward shaper         = 0.6
```

The actor remains bounded and CTBR-based:

```text
31-D -> tanh policy -> 4-D CTBR
```

The old raw-motor / environment-hard-clipping action semantics were not restored.

### 7.2 Reward configuration

The explicit gate reward was restored:

```text
terminating  = -500
ang_vel_l2   = -0.0001
progress     = +20
gate_passed  = +400
lookat_next  = +0.1
```

`mdp.gate_passed` returns:

```text
+1  valid gate pass
-1  crossing the gate plane outside the opening
```

At `dt = 0.01 s`, the effective one-step terms are approximately:

```text
valid gate pass  +4
missed gate      -4
termination      -5
```

This removed the previous reward loophole where a policy could collect substantial look-at reward by hovering toward the gate without racing.

### 7.3 Training scale

The successful run used:

```text
50,000 vector steps
x 4096 environments
= 204.8 million environment interactions
```

This was approximately forty times the 5.12M-interaction V1/V2 experiments.

## 14. Why the estimator likely fails at racing speed

The current production learned-motion model was trained mostly from:

- hover;
- translation S-curves;
- vertical motion;
- yaw sweeps;
- translate+yaw;
- circles;
- Lissajous;
- scripted `racing_like` trajectories.

Those profiles were useful for observability and coupled-motion development, but they are still much milder than the trajectory distribution generated by the successful GT racing policy.

The successful GT policy frequently commands large CTBR actions and produces:

- higher translational speed;
- stronger roll/pitch excursions;
- larger body rates;
- coupled high-thrust turns;
- faster gate-to-gate transitions;
- rapid camera viewpoint changes.

Two failure mechanisms are now suspected and must be measured separately:

### Learned-motion OOD

The TCN may be inaccurate on racing windows even though it was accurate on the earlier replay dataset.

### Visual-update collapse

The camera factor is rejecting almost every frame at racing speed.

Possible rejection stages include:

- insufficient visible semantic corners;
- detector failure;
- mapped-gate association failure;
- pixel residual / association threshold;
- normalized NIS rejection;
- large prior-state error causing the correct gate projection to leave the association basin.

Do not tune these gates blindly. First measure the rejection breakdown.

## 17. Recommended next steps

### Step 1 — Audit GTShadow environment parity

Before using GTShadow as the sole policy-isolation benchmark, compare it against the successful GT task for:

- reset position;
- reset orientation;
- reset linear/angular velocity;
- track geometry;
- episode length;
- termination terms;
- action semantics;
- observation normalizer;
- truth gate progression.

Goal:

```text
GT actor in GTShadow should reproduce the strong GT baseline
independently of whether the shadow estimator succeeds.
```

### Step 2 — Rerun GTShadow with rejection-breakdown diagnostics

Use the latest branch and repeat a small GTShadow evaluation.

For each episode inspect:

```text
gate_reject_reason_counts
gate_reject_stage_counts
```

Especially inspect any 20 s / multi-lap episode.

Do not widen association or NIS thresholds until the dominant rejection reason is known.

### Step 3 — Collect real GT-policy racing motion for learned-motion training

The next learned-motion dataset should be generated from the successful GT PPO itself, not only from scripted `racing_like` trajectories.

Record at 100 Hz:

```text
GT p, v, q
IMU gyro
IMU acceleration
actual / commanded mass-normalized thrust
CTBR command
body rates
gate index
timestamp
```

The existing supervised dataset schema already accepts the essential:

```text
t_s
truth p
truth v
truth q
imu gyro
thrust_b
```

so a GT-policy racing collector can reuse the current TCN training pipeline.

### Step 4 — Evaluate the existing V6.2 TCN offline on racing traces

Before retraining, quantify distribution shift.

Report:

```text
Body-Delta-v norm RMSE
axis RMSE
bias
predicted covariance calibration
error versus speed
error versus |body rate|
error versus collective thrust
error versus roll/pitch
```

This determines whether TCN failure is a dominant source of EKF divergence.

### Step 5 — Train a racing-aware learned-motion model

If racing-trace offline error is poor:

- mix the previous balanced V6.2 data with policy-generated racing data;
- preserve independent validation/test racing trajectories;
- keep the current endpoint-body gravity-compensated Delta-v target unless the new evidence shows the target itself is inadequate;
- use trace-balanced sampling so repeated laps do not dominate the dataset.

Do not replace the old dataset with only one policy trajectory.

### Step 6 — Fix visual correction at racing speed

Use the new rejection breakdown to determine whether the main issue is:

```text
visibility
detector confidence
association
geometry
latency
NIS / covariance
prior-state divergence
```

Only then modify thresholds or detector/perception training.

### Step 7 — Require estimator survival under GT-controlled racing

Before reconnecting the estimator to the actor, require a GTShadow benchmark such as:

```text
full 20 s racing episode
truth gates >= 30
mission progression follows truth
visual corrections remain active
position/velocity error remains bounded
```

The exact numerical estimator threshold should be chosen from measured policy sensitivity, not guessed prematurely.

### Step 8 — Reconnect the strong GT policy to estimated state

Only after Step 7:

```text
estimated p, v, R
 + map
 -> same 31-D
 -> frozen GT PPO
```

Then measure the performance drop.

### Step 9 — Residual/noise policy fine-tuning

If the estimator is bounded but the frozen policy is still fragile, then introduce:

- measured position residuals;
- velocity residuals;
- attitude residuals;
- latency;
- visual dropout;
- estimator covariance / uncertainty if desired.

At that point asymmetric actor-critic / privileged critic training can also be considered.
